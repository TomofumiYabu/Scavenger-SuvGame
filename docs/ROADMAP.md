# AFTERLIGHT 品質向上の行動計画

作成日: 2026-10-16（日本時間） / 状態: P1進行中。AL-001〜003は完了。AL-004ではイベントを1件から合計3件へ広げる（残り2件）。AL-005以降は未着手。

## 1. 目標と前提

ユーザーの目標は、Steam で評価されるサバイバル作品に並ぶ品質へ育てること。最優先の面白さは **探索・生存・選択の緊張感** と確認済み。

最初の到達点を **20〜30分で魅力が伝わり、もう一度遊びたくなる、完成度の高い一地区の体験版** とする。その体験への反応を確認してから製品規模を決める。人気や販売成果は、遊んだ人の反応と公開後の結果で評価する。機能の実装数やテスト通過数だけで達成と判断しない。

継続する前提:

- 荒廃した近未来都市、日本語、一人用、ターン制、静的配信可能なブラウザ版。
- 開発・ビルド・自動テスト・修正は Codex Cloud で完結。GitHub Pages でプレイできる状態を保つ。
- 検証済みの機能単位でコミット・プッシュする。大きな変更は作業ブランチで保存し、安定した段階で main に統合する。
- 現行ルールは `SPEC.md`。この計画は将来の案であり、記載だけで実装済み・仕様確定とは扱わない。
- Steam への実販売はブラウザ版の品質目標とは別の判断。回答が得られるまではブラウザ版を主対象にし、移植しやすい構造を維持する。

## 3. ゲームの中心となる体験

基本の繰り返し:

**手掛かりを読む → 道具と行き先を選ぶ → 危険と時間を使って探索 → 持ち帰る物を選ぶ → 処置・休息・次の準備 → 脱出へ近づく**

磨く柱は次の3つ。

1. **生き残るための取捨選択**: 飲料水を持つか、修理部品を持つか。探索を延長するか、帰路の気力を残すか。
2. **理解できる危険**: 倒壊の兆候、足跡、音、時間帯から危険を推測できる。悪い結果の原因を振り返り、次回は準備を変えられる。
3. **街の中で起きた自分の物語**: 見つけた物や遭遇の結果が次の選択に残り、単なる数値の増減以上の記憶になる。

独自性の仮説は **「救難電波を追って希望に近づくほど、自分の存在も街に知られる」**。無線・騒音・追跡のうち、一つの分かりやすい仕組みを試作して評価する。これは提案段階。背景説明だけの要素にせず、使いたい利点と避けたい代償があるかを検証する。

具体例: 無人の診療所で「手早く回収」「時間をかけて探す」「危険を見て立ち去る」を選ぶ。ライトは探索に有利だが目立つ。薬を持ち帰るには別の荷物を置いていく必要がある。包帯の用途と負傷がつながることで、次の探索準備が変わる。

### P1の上限を先に決める

- 探索方法はまず2種類（手早く / 慎重に）。所要時間・気力・収穫・危険の差を明示する。
- 選択式イベントはまず6件を十分にテストし、成立を確認して12件程度へ増やす。
- アイテムは既存4種を含む8〜12種、容量は重量など1つの単位で管理する。グリッド型の収納パズルは後で判断する。
- 条件分岐する負傷や騒音は、一度に増やさず、独自性の検証に必要な1要素から試す。
- 完全な戦闘システム、巨大な生成マップ、複雑な拠点建築はP1に含めない。

## 6. 技術とコンテンツの進め方

### 維持するもの

TypeScript + Vite、静的配信、純粋なルール関数、固定シードの再現性、Vitest / Playwright、既存の公開導線。現在の2Dターン制には利用できる土台がある。

### 必要になった箇所から整備するもの

- イベント・アイテム・レシピ・調整値を型付きデータへ分離し、参照先ID、条件、到達しない分岐を検証する。
- 行動処理を移動・探索・遭遇などのまとまりに分け、UIから判定理由と結果を取得できるようにする。
- `main.ts` の描画・入力・保存を分割し、操作した箇所のフォーカスとスクロール位置を維持する。
- セーブに形式バージョンと内容バージョンを持たせ、移行前のバックアップ、変換、互換性の確認を設ける。v1の進行を消して更新完了とはしない。
- UI文言を管理しやすい形にして、将来の英語対応や設定を追加しやすくする。
- 絵・音には用途、サイズ、権利、入手元、修正履歴を記録する。追加予算が未定の間は、既存素材と独自に作れる素材で代表場面を作る。

Canvas / PixiJS / Phaser 等の導入は、多数の描画要素や演出で現在のDOM構成が制約になった時に比較する。ゲームルールと保存は描画方式から独立させる。現時点で全面移植は予定しない。

### 初期の対象範囲

デスクトップのマウス・キーボードを主要操作とし、ブラウザ版のスマートフォン操作も維持する。コントローラー、全機種対応、Steam Deckの最適化は、公開対象を決めてから計画する。

## 7. 品質を判定する方法

### 自動で確かめる

- ルール: 資源の増減、費用の二重消費、行動不能、選択の解決、勝敗、乱数の再現。
- 保存: 旧版からの移行、途中イベント、破損、容量制限、書き出し/読み込み、読み込みによる無限収穫の防止。
- コンテンツ: ID参照、イベントの条件と終了、全選択肢の代表経路、アイテム/レシピの参照整合性。
- マップ: 目標への到達、必要資源が存在すること、開始直後の回避不能な詰み。ランダム生成を入れた段階で固定したシード群を検査する。
- UI: 主な操作から脱出まで、敗北と再開始、キーボード、狭幅、セーブ移行、静的サブパス。
- 性能: 検証する環境と測定方法を記録。仮目標は通常行動への応答100ms以内、初回転送5MB程度以内、低速回線で初回操作まで5秒程度。素材追加後に実測して予算を調整する。

### 人が遊んで確かめる

各段階で、プレイ時間、最初に迷った場所、実際に選んだ行動、死因の理解、記憶に残った場面、次に試したい行動を記録する。最初は5人程度の少人数観察を使い、理解できない箇所を見つける。この規模の結果を市場全体の評価とは扱わない。

試遊の仮目標:

- P3: 初見5人中4人が、5分以内に目標と基本操作を自力で理解する。
- P4: 初見5人中3人以上が、終了時に別の方法を試すため再プレイを選ぶ。言葉での評価と実際の行動を分けて記録する。
- 敗北した人が理由と次に変える行動を説明できる。説明できない敗北は表示・予兆・ルールのどこに原因があるか調べる。

「勝率を下げる」「平均時間を伸ばす」だけを目標にしない。難しさと納得感、繰り返しと再挑戦を区別する。自動で最後まで進めることと、面白く遊べることも別に評価する。

協力者の募集や外部への連絡はユーザーが決める。Codexは試遊用ビルド・記録用紙・集計・修正を担当する。最初は手動の記録で始め、利用者を追跡する外部計測サービスを勝手に追加しない。

## 8. 公開・評価・販売の進め方

- P1から変更点と狙いを短く公開記録に残し、公開ページへの感想を次の課題へつなげる。
- P2の体験が成立したら、実際のプレイから短い紹介映像・スクリーンショット・一文の紹介を作る。「何を選び、何が起きるゲームか」を伝える。
- P3〜P4では、参加人数、再プレイ、繰り返される不満、遊び続けた理由を見て訴求と内容を調整する。評価を集める前に大規模なコンテンツ量や販売日を確約しない。
- 公開告知、SNS投稿、ストア公開、支払いが伴うサービスの利用は、その具体的な作業を行う段階でユーザーの方針に従う。今回の計画作成では実施しない。

Steam販売を目標にする場合は、P2の反応を見て別工程を追加する:

1. 配布対象OS、価格帯、ブラウザ無料版との違いを決める。
2. Electronなどのデスクトップ包装を小さく検証し、同じゲームルールでビルドできるか確認する。
3. 起動・終了・画面サイズ・保存場所・更新・必要に応じた実績やSteam連携を検証する。
4. Steamworksの登録、契約、費用、税務・支払情報、素材の権利、ストア審査について、その時点の公式要件を確認する。ユーザーが行う手続きとCloudで行える作業を区別する。
5. 対象OSでの実行と配布用ビルドを検証する。LinuxのブラウザテストだけでWindows/macOS版が完成したとはしない。ユーザーのローカル開発環境を前提にせず、Cloud/CIでの検証手段を先に確保する。

## 9. 進行・見積もり・見直し

役割: Codexは設計案、実装、テスト、調整、文書、コミット・プッシュを担当。ユーザーは面白さ・雰囲気の方向、試遊の評価、追加予算や販売方針を決める。予算を使う素材制作や協力者への連絡を無断では行わない。

直近はP1を上記3つの開発単位に分けて進める。P2以降の期間は、P1の実際の作業量、試遊の人数、絵と音の制作方針が分かった段階で見積もる。現時点では発売日・総制作費を設定しない。各単位の終了時に、成果、残課題、検証、次の優先順位を `PROGRESS.md` に記録する。

| リスク | 早い段階の対処 |
| --- | --- |
| 機能が増えて判断が分かりにくくなる | 一度に一つの仮説を試し、使われない・違いが伝わらない仕組みを整理 |
| マップを広げても同じ操作が続く | 一地区での判断と出来事を評価してから拡張 |
| ランダム要素が理不尽さになる | 予兆・回避策・再現可能なシード・敗因の説明をセットで作る |
| 更新で既存セーブを失う | P1の最初から移行とバックアップを必須にする |
| 絵と音の品質や制作量が揃わない | P2の代表場面で制作基準と必要工数を確認する |
| 品質は上がっても遊んでもらえない | 体験版の反応と紹介の伝わり方を早期に検証する |

優先順位は **進行不能・セーブ保護 → 判断の面白さと理解 → 操作と演出 → 内容の拡張 → 販売固有の機能**。AL-001〜003は実装・自動検証完了。次はAL-004で「崩れた備蓄庫」に2件を加え、第1開発単位の代表イベントを合計3件にする。
